# vllm_bench

Run user-defined vLLM benchmark scenarios through Docker Compose or Modal. Benchmark
scripts and the runner execute on your machine; startup scripts execute in
containers. The same Python library supplies arguments and service addresses to
both. The provider owns service infrastructure; the runner and reports are shared.

## Install

```bash
python -m pip install -e /path/to/vllm_benchmark
```

Build the same package into your service image. Installing the CLI on the host
alone does not make it available in containers. All image dependencies are
installed during the image build, never by the provider at startup.

See `../multi-worker-kalypso/.vllm_bench/configs/base.yaml` and its `.vllm_bench/README.md`
for a complete integration with real service and benchmark scripts.

## Commands

Each user project supplies `.vllm_bench/configs/base.yaml` and named benchmark
configs in the same folder. Commands use the current working directory as the
project root:

```bash
vllm_bench up --config example --scenario baseline
vllm_bench down
vllm_bench run scenarios --config example
vllm_bench report results/local-compare_coordinators/run001
```

`up` requires an explicit scenario and streams container logs during startup and
while running. Ctrl+C stops the environment and saves its logs. Use `up -d` to
start in the background:

```bash
vllm_bench up --config example --scenario baseline -d
```

`up` attaches to an existing environment only when its benchmark and scenario
match. To switch to another environment, run `down` first. `down` also works
when the config has since changed.

`run scenarios --config example` runs every scenario and repeat for the selected
benchmark, starting fresh containers for every trial. It stops a previous `up`
environment first. Failures preserve partial files and continue; Ctrl+C stops
the experiment. Cleanup failures preserve recovery state for `down` and stop
further scheduling. Reports run after cleanup and can be regenerated offline.

To run from another directory, pass the project root, not the config folder:

```bash
vllm_bench --current-dir /path/to/project up --config example --scenario baseline
```

`--current-dir` works before or after the command. It controls config lookup,
script paths, project mounts, snapshots, results, and runtime state. Relative
report paths also resolve from this root.

## Modal

Install the optional provider SDK and authenticate once:

```bash
python -m pip install -e '/path/to/vllm_benchmark[modal]'
modal setup
```

Add `.vllm_bench/configs/modal.yaml`. It can inherit an existing benchmark config:

```yaml
extends: example
provider: modal
base_image: your-registry/benchmark:latest
modal:
  app: vllm-bench
  gpu: T4:1
  cpu: 8
  memory: 16384
  timeout: 14400
  cache_volume: vllm-bench-model-cache
```

```bash
vllm_bench up --config modal --scenario baseline
vllm_bench down
vllm_bench run scenarios --config modal
```

The registry image must contain the service dependencies. The provider copies the
current CLI library into the image without installing dependencies at startup.
Each trial uses one sandbox: selected services start in parallel, use distinct
ports, and share its GPU/CPU allocation. Service `gpus` settings apply to local
Compose; `modal.gpu` allocates GPUs for the whole remote environment. Memory is
in MiB and timeout is the sandbox's maximum lifetime in seconds.

The project ZIP is uploaded and extracted unless `skip_volume_mount` is true.
`bench_util.get_service_path(path)` uploads files or directories generated by a
client benchmark before returning their remote path. Benchmark scripts and
metrics collection still run locally, using HTTPS service tunnels. Scripts must
use the URLs supplied by `bench_util`, including each service's assigned port.

`up` streams sandbox logs and supports `-d`. `down` discovers the saved provider,
stops service processes, downloads service output/logs, and terminates the sandbox.
Results use `results/modal-<name>/runNNN/` and the same offline reports as local
runs. If a sandbox times out or is externally terminated, its combined logs are
saved as `modal.log`; service files may no longer be available for download.

## Config

`.vllm_bench/configs/base.yaml` contains shared settings, service definitions, and benchmark scripts:

```yaml
name: comparison
provider: local
base_image: my-project-benchmark:latest

global_args:
  model: my-model
  max_model_len: 8192

services:
  worker:
    role: worker
    replicas: 2
    startup_script: scripts/start_worker.py
    health_port: 8000
    metrics_path: /metrics
  leader:
    role: leader
    startup_script: scripts/start_leader.py
    health_port: 8000
    metrics_path: /metrics

benchmarks:
  example:
    script: scripts/benchmark.py
    script_args:
      dataset_percentage: 0.01

runs: 1
startup_timeout: 1800
benchmark_timeout: 3600
sample_interval: 1
```

`.vllm_bench/configs/example.yaml` selects one benchmark and declares every scenario's services:

```yaml
benchmark_scenarios:
  benchmark: example
  scenarios:
    - name: baseline
      args:
        coordinator: single_worker
      services: [leader]
    - name: distributed
      args:
        coordinator: round_robin
      services: [leader, worker]
```

`--config example` loads `.vllm_bench/configs/example.yaml` over its sibling
`base.yaml`.
Mappings merge recursively; child values and lists replace base values and lists.
`extends: other_config` inherits a named config before applying overrides.
A YAML file path is also accepted. The option works before or after the command.
Saved results contain the complete merged configuration.

Without `--config`, the CLI reads `base.yaml`. A base without
`benchmark_scenarios` cannot start an environment or a benchmark run. `up` also
requires `--scenario`; it never silently chooses the first scenario.

Scenario `services` is required and must be a nonempty list of known service
names. Only listed services start. Each listed service expands to its configured
replica count. The CLI does not infer dependencies or disable workers based on
scenario arguments. Scenario and benchmark arguments are arbitrary project data.

Names use lowercase letters, digits, underscores, or hyphens, starting with a
letter. Script paths are relative to the project root.
Each replica has its own container, published host port, and output directory.
`health_path` defaults to `/health`; omit `metrics_path` for services without
metrics. Startup scripts must bind to `0.0.0.0` at their configured health port.
Scripts run in the foreground; returning from a startup script stops its service.

Optional fields:

- `skip_volume_mount: true`: use code already installed in the image; omit the
  project mount and ZIP. Context and output are still mounted.
- `image_workdir`: image project directory when skipping the project mount;
  defaults to `/workspace/project`.
- Service `gpus: all` or `gpus: ["0"]`: NVIDIA GPU allocation. Omit for CPU.
- Service `environment`: extra string environment values for that service.

The image must support the selected hardware. Exposing GPU devices requires a
compatible Docker host; detecting no GPU does not turn a CUDA-only vLLM build
into a CPU build. Set GPU allocations per service to control sharing.

## Script library

```python
from vllm_bench import bench_util

model = bench_util.get_global_arg("model")
options = bench_util.get_global_args()
coordinator = bench_util.get_scenario_arg("coordinator")
fraction = bench_util.get_benchmark_arg("dataset_percentage", 1.0)
repeat = bench_util.current_run
benchmark = bench_util.current_benchmark
output = bench_util.get_output_dir()
```

Other helpers:

- `get_project_dir()` returns the project root in the calling environment.
- `get_service()` returns the calling startup's name, role, replica, and URL;
  it returns `None` in client benchmark scripts.
- `get_leader_url()` and `get_worker_urls()` choose the correct addresses for
  the calling environment. Disabled workers yield an empty list.
- `get_service_url("icp")` returns a named service. For a replicated group, use
  its individual name such as `worker-1`.
- `get_service_url("icp", internal=True)` returns the container address when
  constructing a benchmark payload that the leader will execute.
- `get_service_path(local_path)` translates project/trial paths in a client
  benchmark to paths readable inside the containers.
- `get_gpu_count()`, `is_gpu_available()`, and `is_cpu()` inspect the calling
  environment using `nvidia-smi` without importing PyTorch.

Benchmark scripts write `response.json` in `get_output_dir()`. Arbitrary JSON
is preserved. When present, a numeric `latency_sec` and a `results` list provide
additional summary fields; process runtime is measured independently.

## Files and infrastructure

The project is mounted read-only at `/workspace/project`. Each trial directory
is mounted writable at `/run/vllm-bench/trial`; `get_output_dir()` selects the
client trial directory or a replica's service subdirectory. Docker logs and GPU
samples are saved under `services/<group>-<replica>/`.

The generated Compose file, resolved per-service contexts, and provider IDs are
saved under the trial's `.provider/`. The active state is recorded under the
project's `.vllm_bench/state.json`. Host ports bind to `127.0.0.1` and container addresses
use Compose DNS. A named model-cache volume persists after `down`.

By default, each run also saves a ZIP of nonignored project files. Results,
environments, native binaries, caches, `.env` files, and generated wheels are
excluded. The live local project mount reflects subsequent edits; keep files
unchanged during a run when comparing its saved snapshot.

See [RESULT_FORMAT.md](RESULT_FORMAT.md) for the saved contract and reports.

## Development checks

```bash
python -m unittest discover -s tests
python tests/compose_smoke.py --image an-image-containing-vllm-benchmark
```

The opt-in Compose check launches HTTP stand-ins with Prometheus metrics. It
checks lifecycle, endpoints, mounting, scenarios, collection, and reports without
loading any model or allocating cloud resources.
